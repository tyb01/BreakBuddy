PawsUp production readiness review — 2 November 2026

This review concerns the source in this checkout: com.pawsup, version 1.0.4 (5), minimum API 24, target API 35. It does not establish what binary is currently published on Google Play. Findings below distinguish source-confirmed behavior, platform constraints documented by Google, and recommendations. No connected Android device was available. No Play Console, real purchase, customer usage, or production crash data was available. Product effectiveness cannot be established from code.

**Assessment: hold a production release until monitoring, billing, platform compatibility, and release security are corrected.** The cat experience is implemented, but the reliability of the core promise is not established, and several defects are directly visible in the source.

**What a user gets today**

1. A welcome screen, guided requests for usage access, display-over-apps access, and notification permission, followed by a Miso introduction video and installed-app picker.
2. A searchable list of launchable apps. Users choose which packages to monitor. This is app-level monitoring; the app does not inspect scrolling, feed content, or individual websites.
3. A common visit limit, default 15 minutes, adjustable from 1–60 minutes. A common break duration, default 2 minutes, adjustable from 1–30 minutes.
4. While the service is running, it polls usage events every two seconds. A continuous observed stay in one selected package starts a timer. Switching packages resets that timer.
5. At the threshold it attempts to launch a full-screen activity with the chosen cat: entrance video, looping idle video, countdown, changing dialogue, pet taps/purrs, and an outro. The configured countdown starts after the entrance. An optional guest visit pauses it. A recap toast is scheduled six seconds after completion.
6. Five cats: Miso and Mocha are free; Yuki, Shadow, and Biscuit have subscription purchase paths. A cafe subscription covers all cats. The screen has monthly/yearly choices. Actual live prices and available offers were not verified; USD amounts in code are fallback display strings.
7. After at least three completed breaks, an eligible break has a 15% chance to schedule an unowned premium cat visit after 20–40 seconds. Visits last up to eight seconds, with a seven-day limit per guest cat. A button opens the paywall. Bundle owners are excluded.
8. Home, Cafe, and Reliability tabs; a Monitor me toggle; permission status; battery-exemption and manufacturer-settings shortcuts; and a privacy-policy link.
9. Local preferences include selected apps, settings, cat access, completed-break and pet totals, and guest timestamps. There is no implemented user-facing usage-history dashboard, daily budget, schedule, or task manager.

The README's screen-time-enforcer description overstates the implementation. The app inserts an interruption; it does not implement a persistent lock on selected apps. Share-card and long-press escape helpers exist but are not wired into the active break screen.

**Further user-experience and correctness gaps**

- **Breaks can be left without an explicit product policy.** `BreakOverlayActivity` does not install Back handling or enforce a blocked-app cooldown. Home/Recents are not prevented. The long-press escape component is unused. Choose a transparent reminder/commitment model, provide a visible emergency exit, and record skipped versus completed breaks. Do not promise an unbreakable block.
- **A break keeps the display on and asks Android to turn it on/show over the lock screen.** The flags are set in `BreakOverlayActivity.kt:48`. Combined with missing screen-off accounting this can produce unwanted interruptions. Remove unnecessary wake/lock-screen behavior and test calls, media, alarms, and unlocking. There are no implemented quiet hours or sound controls.
- **Video failure has no recovery.** Both video components depend on normal playback callbacks and lack `onPlayerError` handling or timeout fallback. Entrance failure prevents the break countdown from starting; outro failure prevents normal completion; the onboarding introduction likewise depends on video completion. All expected 15 cat videos, five WebP posters, and two sounds are present, but file presence does not prove decoder compatibility. Add a static fallback that preserves timer and navigation.
- **Lifecycle restoration is incomplete.** The break ViewModel saves only launch inputs, not the active deadline/state. The player is recreated on configuration changes while the ViewModel may survive. `onEntranceStarted` also rewrites displayed seconds. Process death starts a fresh break; rotation/media-state alignment requires testing. The onboarding step is an in-memory Activity field and resets on recreation. Persist the minimum user-visible progress and derive the screen/player state from it.
- **Reliability status is misleading.** `SettingsActivity.kt:379` hardcodes the manufacturer-autostart row to false, so it cannot turn green after the user fixes it. The instruction that all rows must be green is impossible on those devices. The screen also lacks a last successful poll/trigger heartbeat. Use verified, unknown, and needs-action states rather than inventing certainty.
- **Permission recovery is incomplete.** The settings screen shows denied usage/overlay/notification status without corresponding repair actions. Onboarding refuses to proceed unless notifications are granted, despite Android permitting foreground-service startup without that runtime grant. Provide an explanation, optional notification choice where appropriate, and settings recovery after permanent denial. [Official notification permission behavior](https://developer.android.com/develop/ui/compose/notifications/notification-permission).
- **Users can finish setup with no apps selected.** Monitoring defaults on, but the service simply returns when the selection is empty. Show a clear inactive state and an action to select apps. Do not imply protection from the switch alone.
- **Premium selection and entitlement diverge.** The service loads the saved active cat without checking current ownership. Expiration can lock a cafe tile while the already-selected paid cat keeps appearing. Reconcile the active selection with verified entitlement and explain any fallback.
- **Purchase success copy is inconsistent with behavior.** Success says the cat will appear next time, but the purchase path never changes `activeCatId`. Let the user select the newly acquired cat or change the message. A cafe purchase also uses the individual cat's success title.
- **Purchase verification and acknowledgement recovery need strengthening.** The purchase token is emitted but not used for verification; acknowledgement results are ignored. No backend verification is present in this checkout. Google recommends secure backend verification, but absence of a backend alone is not proof of a policy violation. Establish verified entitlement and acknowledgement retry handling. [Billing security](https://developer.android.com/google/play/billing/security).
- **Pet interaction lacks accessibility semantics.** The active tap zone is an invisible Box using raw pointer input, without an accessible click action or label. Implement a labeled accessible action, then test TalkBack, switch access, large fonts, landscape, and contrast. Fixed offsets in the dialogue/countdown need visual testing before declaring clipping. [Compose semantics](https://developer.android.com/develop/ui/compose/accessibility/semantics).
- **Local counters can lose concurrent updates.** Pet and break counters read a value before entering DataStore's edit transaction. Concurrent pet taps can read the same old value. Increment inside the transaction; make break completion idempotent. App-selection toggles also compute from asynchronously collected state and deserve rapid-input testing.
- **Installed-app list can contain duplicate package keys.** The repository maps every launcher activity without deduplicating packages, while the list uses packageName as its unique key. Apps with multiple launcher entries can break that assumption. Deduplicate, and exclude the current applicationId rather than the hardcoded release package (the debug package differs).
- **Performance is unmeasured.** The service scans a 10–120-minute event window every two seconds. Posters are decoded and chroma-keyed at process startup, including service-created processes. Assets total 47,873,242 bytes, including duplicate PNG/WebP posters and unused onboarding images. These are concrete optimization opportunities, not measured battery drain or store download size. Profile polling, memory, cold starts, video decoding, and installed size before making performance claims.

**Privacy and trust**

No app-owned analytics uploader, account system, advertising SDK, or custom backend was found in the inspected source/dependencies. That is narrower than proving zero data transfer: Google Play Billing participates in purchases, and the previously generated merged manifest includes INTERNET permission.

`android:allowBackup="true"` is explicit and no custom backup/data-extraction exclusions are declared. Android Auto Backup can include internal app files. Consequently, blanket claims that all information always stays on the phone, or uninstall permanently removes every copy, need qualification. Define backup and device-transfer behavior, reconcile restored settings with fresh permissions and purchases, and offer local reset/delete controls. [Official Auto Backup documentation](https://developer.android.com/identity/data/autobackup).

The current app links to `https://www.techniact.com/apps/pawsup/privacy-policy`; the web tool could not retrieve it. This review does not assert that the page is down or missing. Its actual content, accessibility, legal contact details, and consistency with the Play Data safety form remain unverified. **Required release evidence**

1. A successful reproducible lint/build pipeline, supported target/Billing dependencies, protected signing configuration, and review of release merged permissions.
2. Automated timer traces for switching, screen-off, permission loss, wall-clock changes, service recreation, and break-trigger retry; billing tests for offline failures, restore, renewal, cancellation, expiry, pending transactions, and failed acknowledgement.
3. Device tests on every supported API boundary, especially 24/25 if retained, 26, 31, 33, 35, and 36, plus representative Samsung/Xiaomi-class manufacturer restrictions. Cover reboot, force-stop/user stop, Doze, battery saver, process death, and permission revocation. Do not claim restart after user force-stop without platform support.
4. Break tests for Back/Home/Recents, rotation, process recreation, calls/alarms/media, missing or unsupported media, sound preferences, lock/unlock, and accessibility.
5. Real Play license-tester purchase and restore evidence, correct localized pricing and renewal disclosure, a working privacy page, accurate Data safety answers, and crash/ANR/battery monitoring that respects the privacy model.
